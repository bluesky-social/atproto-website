Many popular apps aim for synonymity with their function. The name Duolingo practically describes the entire ecosystem of language learning apps; WhatsApp is globally associated with messaging. You know what this reminds us of? That's right, [**the Unix philosophy**](https://en.wikipedia.org/wiki/Unix_philosophy)!

That's right, I know what you're thinking: “you probably bring this up every chance you get!” Well, so what, it's very useful! The Unix philosophy says that programs — or user-facing apps — should try to **do one thing well**. That's why, on a modern Linux system, what we think of as key OS functionality is provided by entirely different programs: `df` for checking disk space, `curl` for making web requests, and so on. Some of these we take for granted as more like core *verbs* than applications per se, but, really, that's just evidence of the philosophy working well; you can `curl` a thousand different ways, but no matter what, you know when to use that particular muscle.

There are varying opinions about how well this philosophy maps onto modern application development, but it is generally true that committing to making a *dedicated* event planning app, or a dedicated marketplace-style app, is both sticky for a user base and clarifying in terms of scope. These are two very good things to be, and they are, of course, supported by the bet we're making on the Atmosphere — that identity and data should be portable, and switching between applications should not come with the high cost it currently does elsewhere, i.e., needing to recreate your presence and your social graph in a proprietary network.

So far, though, we've only borne that out for *individuals*: individuals' followers, individuals' data, individuals' individually created calendar events or web presences. This is powerful in its own right, but doesn't really map onto the way that we expect organizational continuity, or delegation, or simply shared work to actually *work* in practice. Open Social Groups change that, and they do it in a way that's native to the Atmosphere.

This was for two reasons: one, Grain has already added support for creating Groups directly, and two, it was simpler to initially showcase it within a single app, in the photo sharing mode of Grain.

## Group Atmosphere Logins

Let's demonstrate that with [pckt.blog](pckt.blog), a popular blogging app that implements [standard.site](https://standard.site/).

<Image src={pcktAuth} alt="Pckt authentication interface" />

Signing in gets us the usual [pckt.blog](pckt.blog) interface and feature set — this is early days for Spaces support across the Atmosphere — but as a starting point, from a group's point of view, this is a good thing. It means that drafts and publications can be owned by shared identities rather than individuals, and it eliminates any need for pckt to implement group management on its own; it only has to support the Spaces features of the protocol, so it can offload the management interface to sites like [opensocial.fyi](opensocial.fyi).

You can also see how this could provide a solid foundation for subscriber-only or gated content. Again, the actual role management can be handled off-Pckt — [opensocial.fyi](opensocial.fyi) has a preliminary interface for this right now:

This way, you can manage subscription flows and subscriber-only channels the way that other platforms need an additional SaaS layer for; e.g., to ensure that paying members get access to both paywalled content, and a chat channel, and so on, all using the same accounts on the Atmosphere.

## Moving Forward

In the last two weeks, we've shown off Grain for photo sharing, PDSls for data management, opensocial.fyi for group administration, and pckt.blog for authoring. These are all implementing the Spaces APIs as they stand now, and showcasing part of the vision for Open Social Groups. Each of them does one thing well — and, considering that many of them are the product of a solo developer, this is crucial for sustainability. The Atmosphere, in turn, makes it possible for each of these apps to get to critical mass on their own, by letting them leverage first that existing social graph and now the ability to further annotate it with mutually shared, overlapping, enforceable boundaries.

Developing opensocial.fyi has been a great way to explore the Spaces APIs and show off what end-to-end application support might look like. On a fundamental level, building real stuff to exercise protocol designs is important! As we finalize the protocol, our prototypes will change, but the vision for Open Social Groups is here now: a way to create shared identities, with shared data and shared access control, that can be used across the Atmosphere.

Get excited!! We're still releasing breaking changes to Spaces on a weekly basis, but we're just about finished with the major churn. In the next few weeks, this blog will drill into solutions for syncing Spaces at scale, and provide some best practices and implementation patterns.
