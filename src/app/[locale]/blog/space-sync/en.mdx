This week we want to show how Spaces handle one of our core primitives: sync. And the answer may surprise you. **We plan for Space sync to become fully compatible with Jestream.** This is great news, and directly addresses one of our core goals with Spaces — it means that, for most developers, there are not going to be two dramatically different ways of working with the protocol for public and non-public data. **If you've built an app that consumes public atproto data from Jetstream, consuming space data should look very familiar.**

## Why Spaces Need Their Own Sync

Public atproto data flows through relays. Every PDS broadcasts its commits, a relay aggregates them into the firehose, and services like Jetstream turn that into JSON you can filter by collection. Spaces don't work that way. Each space is its own sync boundary; Spaces data is assumed to be non-public. In other words, we don't take for granted the ability to rebroadcast this data. There's no relay carrying space records across the network. We want data shared directly with the parties who have access.

To build a view of a space in a consistent and efficient way, an app has to get a credential for the space, find out which repos have written into it, backfill each of those repos from whichever PDS hosts it, register for notifications about new writes, and keep track of account changes like deactivations and deletions. We haven't talked much about these aspects yet because the Spaces protocol hasn't been finalized, but you would not expect every production Spaces app to have to solve this on their own.

Separately, we *have* talked a lot lately about the ability to [self-host Jetstream](https://atproto.com/blog/introducing-bluesky-protocol-services#jetstream-v2-network-replay). This is important to our broader ecosystem goals; we provide a high-scale Jetstream for most developers that serves data from our own Relays, but the new replay functionality in Jetstream can be computationally expensive at scale, and we absolutely don't want to be the sole arbiter of those costs.

Soon, there will be **an even better reason to host your own Jetstream** — as a secure endpoint for Spaces data. As with the entire atproto stack, Jetstream can scale down to a point where it consumes very few resources; you don't see this with the public Jetstream rebroadcasting every record on the network, but a Spaces-only Jetstream will start out much more manageable. If you have 10 users, you only have access to those 10 users' relevant spaces.

## Consuming the Stream

Your apps will be able to read from the sync service with any up-to-date Jetstream client: e.g., the [TypeScript SDK](https://bsky.network/docs/jetstream), or a [raw websocket](https://endpoints.bsky.app/#jetstream/tag/jetstream-websocket/GET/subscribe) or anything in between. A Spaces-compatible Jetstream would use the same replay-then-live model: you can start from a saved cursor and read through the archive, and eventually cut over to live events — or just start there.

```go
client, err := jetstream.Subscribe(syncURL,
	jetstream.WithCollection("com.example.note"),
	jetstream.WithAfterSeq(cursor),
)
if err != nil {
	return err
}
defer client.Close()

for batch, err := range client.Events(ctx) {
	if err != nil {
		return err
	}
	for _, event := range batch.Events() {
		// event.Space is the space the record belongs to.
		// event.DID is still the record's author.
		if err := applyEvent(ctx, event); err != nil {
			return err
		}
	}
	if err := saveCursor(ctx, batch.LastCursor()); err != nil {
		return err
	}
}
```

The main difference from public Jetstream is the `space` field on each event. One stream provides every space the service follows, so the same author can write a record with the same collection and record key into two different spaces. There are also a couple of new event kinds for space-level changes, like a writer being removed from a space or a space being deleted.

The stream is meant for your app's backend; i.e., not for browsers. It contains records from every space the service follows, so your app still decides which viewers can see what.

## Identity on the Server Side

A Jetstream for public data doesn't need anyone's permission to read the firehose. A sync service for Spaces does, and the way it gets that permission is what makes it possible to run one without changing the trust model of the network.

The sync service doesn't have an account or a password of its own, and it never holds users' OAuth tokens. When it needs to read a space, it asks for a short-lived delegation from a user who already has read access to that space. It exchanges that delegation with the space's authority for a credential, and the authority determines whether that user is a member. If the user signs out or loses access, the sync service has to find another eligible reader or stop syncing that space.

Write notifications work through identity as well. The service publishes its own service identity in a DID document, and space authorities send signed notifications to it when new records are written. Those signatures are checked against the authority's DID keys, so the service only acts on notifications that actually came from the authority for that space. Account-level changes, like deactivations, come from the public Jetstream, so when a member deactivates their account, the stream tells your app to hide their records in every space.

## Jetstream Spaces Prototypes

In the current prototype, the sync service runs alongside an app and borrows read access from that app's signed-in users.

For example, here's a demo of *trails*, a Strava-like app for sharing runs and rides, which is currently built on Spaces, using an adapted version of Jetstream sync. A user can share their runs and rides as atproto records with other Space members, who, in turn, can send them a “cheer” — which references the original run or ride record in its Lexicon, just like a like. Jetstream primitives are used to sync and materialize these views, much as they do in our [Statusphere](https://atproto.com/guides/statusphere-tutorial) example.
