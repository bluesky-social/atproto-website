In this tutorial, you'll use the Spaces primitives to build a private calendar on atproto. This will be data that only you — and any authorized apps — can read. You'll use [Lexicon Community](https://lexicon.community/)-defined calendar [Lexicons](/guides/lexicon), along with the Spaces TypeScript SDK. 


## Prerequisites

You should have installed:

- Node.js 22+

On platforms supported by [homebrew](https://brew.sh), you can install it with:

```bash
brew install node
```

You'll also need an account on a *PDS that supports Spaces*. As of December 1, 2026, the [reference PDS](https://github.com/bluesky-social/pds) includes support for Spaces.

<Note>
App passwords can't access spaces. This tutorial logs in with your full account password, so use a test account. Production apps should use [OAuth](/guides/auth).
</Note>

## Part 3: Open your calendar

Next, add an `openCalendar()` function:
- This space will be keyed as `personal` because you aren't expecting to share it.
- Look for it with `listSpaces`; create it the first time.
- Call `createSpace()` with a `personalspace` policy: only the authority has access.
- Everything here goes to your own repo on your own PDS, so no further credentials are needed.
- Finally, return the Space with `openSpace()`.

<S05 />

## Conclusion

This is one of the most minimal examples of working with atproto Spaces. You wrote logic to create a new Space, wrote to the space, and read it back on the CLI and in a web interface. atproto can be as straightforward as that: among other things, it's a content-addressible storage interface, now with support for non-public data!

For another example of using atproto Spaces for private data, see [Airspace](https://getair.space/)!

Next, refer to [Spaces data](/guides/spaces-data) for a full set of read-write operations, or move on to a multi-user example in [Build a Shared Space App](/guides/shared-space-tutorial).
